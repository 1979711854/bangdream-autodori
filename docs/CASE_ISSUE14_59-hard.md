# 案例：#59-hard「ふわふわ時間」恒定 miss 1（issue #14）

> 完整复盘：现象、四次失败的原因、真实问题、最终改动、验证与预防。
> 相关条目：`AGENTS.md` 第 8 节第一条、`docs/SONG_ISSUES.md` 3.7 与第 4 节。
> 结案日期 2026-11-02，用户实机确认「左起第 5 轨的绿条结尾没有松手」。

---

## 1. 问题现象

| 项 | 值 |
|---|---|
| 曲目 | `ふわふわ時間`，曲目 id `59`，难度 `hard` |
| 版本 | v1.3.5（源码运行，非打包 exe） |
| 结算 | `perfect 383 / miss 1`，`great/good/bad = 0`，`fast/slow = 0` |
| maxcombo | 每次都是 `198` |
| 复现率 | 用户 5 局（11-02 09:04~09:27）+ 本机 2 局（11:31、11:50）全部一致；另有 12:06 一局是错误覆盖试验（`miss 2`），不计入复现 |
| 修复后 | 12:22:49 那局 **`perfect 384 / miss 0 / maxcombo 384`**（同一台机器、同一版本代码 + 本次覆盖） |
| 判定点总数 | 384（`perfect + miss` 与 Bestdori 谱面完全一致，**总数上看不出缺音**） |

用户慢放后的原话：

> combo 197 的时候，左起第 5 轨的绿条结尾没有松手，导致 miss。
> 同一拍左起第 2 轨的绿条结尾是打上了的，所以 combo 短暂到 198 之后才断。

---

## 2. 真实问题（一句话）

Bestdori 把 beat 135 / 左起第 5 轨（lane 4）的那条绿条**结尾**标成了 `flick: true`，
而游戏里它是一条**判定时刻松手**的普通/蓄力尾。

bot 的手势分支是：

```python
end_flick = note_data["connections"][-1].get("flick")
if end_flick:
    finger_end_time = to_time + 80      # 判定后再滑 80ms 才抬手
else:
    finger_end_time = to_time           # 判定时刻立即抬手
```

于是 bot 在 45.000s 开始滑动、45.080s 才抬手；游戏在 45.000s 要的就是「松手」，
手指还在划 → 尾判 MISS。同拍的第 2 轨（lane 1）那条没有 `flick`，正常松手 → 命中，
这就是「同拍两条绿条尾，一条中一条掉」的直接原因。

与 `#147 / #674 / #144-hard / #710-expert` 的「fever 滑条尾被错标成 flick」同族，
属于**数据标注错误**，不是时序问题、也不是手势逻辑缺陷。

---

## 3. 四次失败：做了什么、为什么没找到

### 3.1 第一次：方向 flick 反推错（已否证）

- **依据**：谱面里 `(135,4)` 带 flick，该曲 BMS 在 Bestdori cn/jp 都取不到（返回
  14084 字节 SPA 兜底页），方向只能靠 `chart.infer_flick_direction` 轨迹反推，
  它把轨迹 `5→4` 推成 `R`。
- **改动**：BMS 取不到时不再猜方向，一律上划。
- **实机结果**：11:50 那局仍 `miss 1 / maxcombo 198`（日志确实出现新文案，证明跑的是新代码）。
- **为什么失败**：
  1. 只检查了「bot 谱面里那个位置是什么」，**没有验证游戏里那个位置要什么手势**；
  2. 用 `maxcombo` 反推 miss 位置时，默认「判定点顺序 = 谱面顺序」，把同拍两条尾
     的先后当成确定事实 —— 实际上下两条尾谁先判不确定，第 198 / 199 都能解释
     `maxcombo=198`；
  3. 换方向（R → 上划）后结果一个字没变，这本该立刻说明「问题不在方向」，
     却继续沿用时序推理。

### 3.2 第二次：跨指同帧（已否证，且实验根本没跑起来）

- **依据**：`(135,1)` 的抬手在 45000.0ms，`(135,4)` 的滑动在 45000.00001ms，
  两个动作落在同一个 minitouch commit；`#409-special` 台账里「长条头与另一指 move
  同帧」的 miss 2 看起来同族。
- **改动**：切帧判据从「同指」放宽到「跨指」。
- **实机结果**：**该改动从未真正跑过**。11:50 那局是「禁用反推」版（切帧还没写），
  12:06 那局日志写的是「判定点独占帧: 本局 20 处」，而跨指判据下离线算出来是 27 处
  —— 说明 12:06 跑的仍是旧判据。所谓「加了切帧仍 miss」其实没有证据。
- **为什么失败**：
  1. 没核对改动是否生效，就把那两局当成「跨指假设已否证」，浪费一轮实机；
  2. 即使生效，同帧也只是表象：它只能解释「为什么这条尾的抬手比别人更靠前」，
     解释不了「为什么另一条同拍尾没事」。真正能解释差异的是**两条尾的字段不同**
     （一条有 flick、一条没有）。

### 3.3 第三次：缩滑条 + 补单键（已否证，且让结果变差）

- **依据**：用户说「丢的音符是普通 note，不是滑键」。
- **改动**：把那条 4 节点滑条的最后一张删掉（让滑条在 beat 134 收尾），
  再补一个 `Single(lane1, beat135)`。
- **实机结果**：12:06 那局 `perfect 382 / miss 2 / maxcombo 196`，动作 4541（原 4573）；
  用户直接看到「长滑条突然断了」。
- **为什么失败**：
  1. 把用户的「普通 note」理解成「那里不是滑条」，事实是**滑条还在**，只是结尾要松手；
  2. 动谱面时**删了已有音符**（滑条最后一节），直接让一段判定失效，miss 从 1 变 2；
  3. 仍没有先确认「游戏里那个音符在哪个轨、什么形态」。

### 3.4 第四次：全局给普通滑条尾加抬手余量（已回滚）

- **依据**：lagdump 显示 up 的 lag 中位 +0.6ms、p10 -3.1ms、最坏 -8.5ms，而普通尾
  恰在判定时刻抬手，理论上可能「判定前松手」。
- **改动**：`END_PAD_MS = 10`，所有非 flick 尾抬手延后 10ms。
- **实机结果**：12:18:54 那局 `perfect 383 / miss 1`（日志「判定点独占帧 21 处」，
  确认跑的是这一版），miss 没变。
- **为什么失败**：
  1. 方向对了一半（时序确实紧），但**改错了对象**：掉的是**带 flick 的那条**，
     它 up 在判定后 80ms，完全不受这个余量影响；
  2. 全局改动面太大，用户明确反对：「很容易误伤以前已经 AP 的歌曲」。

### 3.5 四次失败的共同原因（为什么一直没找到真正错误）

1. **只信 bot 侧数据，缺「游戏侧对照」**。谱面 JSON、动作表、lagdump 都只能说明
   bot 打算做什么，说明不了游戏要什么。四次里前三次都没有拿「用户看到的画面」
   去核对，直到用户慢放指出「第 5 轨没松手」才闭环。
2. **把「能解释现象的一个假设」当成「唯一原因」**。maxcombo=198 本来就有两种解，
   却按单解推理；同帧、方向、时序都能自圆其说，就被当成结论。
3. **没有做「一次只改一处 + 确认改动真的生效」的隔离实验**。第二次改动实际没生效
   却按「已验证」处理，白白消耗一轮用户实机。
4. **改谱面时动了已有音符**。缩滑条是这次最严重的错误：数据侧只应「追加」或
   「改字段」，删音符等于把一段判死。
5. **默认「全局修」比「单曲修」正确**。全局手势改动会同时影响所有已 AP 的曲目，
   风险与收益完全不对等；这类单曲问题应当只改覆盖。

## 4. 最终改动（只改这一首，不动代码）

文件：`assets/chart_overrides/59-hard.json`（完整谱面覆盖，Bestdori 原格式）

```diff
  "connections": [
      {"lane": 5, "beat": 132, "charge": true},
      {"lane": 4, "beat": 133, "charge": true},
      {"lane": 5, "beat": 134, "charge": true},
-     {"lane": 4, "beat": 135, "flick": true}
+     {"lane": 4, "beat": 135}
  ]
```

只删 `flick`，`lane`/`beat`/`charge` 与其它所有音符一字未改。
`src/chart.py` 与 v1.3.5 完全一致（抬手余量、跨指切帧两处试验性改动已全部撤回）。

## 6. 后续预防建议

1. **恒定 miss 先问「游戏里长什么样」**：音符类型、轨位、断 combo 的时间。
   用户的一句慢放描述，胜过三轮数据推理。
2. **`maxcombo` 反推必须列全部解**：miss 可能在「第 N+1 个」也可能在
   「总数 − N 个」，两条都要对照用户观察确认后再动手。
3. **改谱面只追加或改字段，不删已有音符**。删滑条节点会截断长条，一次能干出两个 miss。
4. **一次只改一处，并确认生效**。数据侧看 `Local chart override` / `flick 尾统计` /
   动作条数；代码侧看新增日志指纹（如「判定点独占帧 N 处」）。
5. **单曲问题优先数据侧覆盖**，不要改全局手势。用户 2026-11-02 明确：
   全局改动很容易误伤已经 AP 的曲目。
6. **同拍多尾时用「差异对照」而不是猜时序**：两条尾巴的字段差异（有无 `flick`、
   有无 `charge`）比服务端 lag 更能定位问题。
7. **同一首曲最多试一轮假设**：换假设前必须有一个能区分两种假设的观测点，
   否则就是重复消耗用户实机。
